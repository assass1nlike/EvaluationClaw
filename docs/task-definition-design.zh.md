本文是 TaskDefinition 扩展设计方案，尚未实现。

建议把 TaskDefinition 定义为：一个任务向被测对象提供什么信息、允许什么操作、怎样随交互演化，以及根据什么证据评分的完整契约。常见任务使用简短的声明；复杂任务通过同一契约下的可执行组件实现。

通用性来自这些组成部分可以独立组合，并有受约束的扩展接口。验收标准是保持任务的输入、权限、交互、终止和评分语义，不只是能够保存外部 JSON。

比较范围按本次确认：AutoBencher、Benchmark-Agent、Gym-Anything、AutoControl-Arena、Petri；八类常规需求对应的人工参照；D7 的 Who&When 和 D12 的 AgentDojo。YourBench 不在范围内。

当前主要约束集中在：五种题型同时决定输入与评分路径；模型输入基本是单条文本；多轮交互限制在少量用户追问；正式 agent 环境限定 Docker/VM；actors 和干预绑定 Docker；workflow 是固定顺序阶段；自定义非 agent 评分主要只有 python_tests；结果以一个 0–1 分数为中心。现有环境、工具、judge 和证据实现可以复用，但这些限制不宜成为通用表示的边界。

**推荐的 TaskDefinition 结构**

以下是模块结构，不要求 Builder 每次填写所有模块：

```text
TaskDefinition
  schema_version, id
  content       实际输入、上下文、选项、要求的输出
  assets        文档、图像、代码、镜像/快照等资源引用
  environment   初始状态、操作接口和生命周期
  interaction   参与者、会话、交互策略和任务预算
  evaluation    参考、评价依据、评分实现及指标定义
  provenance    来源、版本、原记录映射
  annotations   题型、语言、学科、构题 effort 等可选描述
```

题型继续保留为常用模板和报告标签。Runner 根据明确的交互协议及评分协议执行，不再因 `choice` 就固定添加“只输出选项 ID”，也不因 `generation` 就固定调用通用 LLM judge。

任务定义只保存一次。运行视图、给目标的视图和给 LaaJ 的视图从它派生。`BenchmarkItem` 可以继续承担兼容入口，但不应再成为一份与定义并行维护、依赖 metadata 补充执行语义的第二份真相。

维度归属是任务与某个用户需求/题集的关联。外部题不需要编造一个内在 dimension，也不默认赋予 E3；原始难度、EvalClaw 构题 effort 分开记录。

**1. content：准确表达被测对象实际接收的内容**

支持有序消息，每条消息包含角色、内容块及必要的工具调用关联。内容块支持文本、结构化数据和带媒体类型的资源引用。长文档可存文件，通过明确的装载方式进入请求；引用文件不意味着自动给目标增加读文件工具。

区分三种用法：

- 普通材料：Who&When 的历史是待分析数据，不能变成当前模型已经参与的历史。
- 预置上下文：MRCR 的历史需要保持原生 user/assistant 角色顺序，但其中的 assistant 内容不是本次模型生成。
- 实际交互：SEA-HELM 多轮任务后续回合使用当前模型刚生成的回答。

保留原始输入及确定性呈现方式，记录最终送入模型的消息。选项已经写进原文时，可以不另外解析 options；确有结构化选项时也不重复渲染。输出契约可描述文本、JSON、代码、文件、补丁或指定环境结果，不局限于一个答案字符串。

few-shot 示例、答案前缀、stop 条件和上下文装载/截断规则必须有出处。超出模型上下文能力时明确报告不可执行，不能静默截断后声称是同一道题。LaaJ 可分页读取长材料，目标模型的呈现仍遵循原任务要求。

**2. assets：统一引用和可见性，但不把一切公开给目标**

每份资源至少支持稳定 ID、包内相对位置或版本固定的外部引用、媒体类型和内容摘要校验。文本可以内联，大文件、代码目录、镜像和快照通过引用保存。文件路径、镜像标签之外还要保留足以确定内容的版本或 digest。

资源用途和访问权限明确记录：作为目标输入、挂入环境、仅供环境内部逻辑、供评分使用。参与者的可见性与写权限由运行时落实，不能只有说明文字。

不要把所有名为 answer 的内容都自动隐藏。Who&When 原协议会把原问题的答案作为归因依据提供给模型；真正需要保密的是责任 agent/步骤标签。参考代码与公开示例也可能同时存在，必须按原协议映射。

来源信息保留以便核查；给 LaaJ 的视图在不破坏语义的情况下隐藏方法标识。资源缺失、不可访问、未提供和不适用使用明确状态，不编造空答案代替。

**3. environment：把环境能力从 Docker/VM 的部署方式中独立出来**

环境需要表达两个方面：实际状态与操作语义，以及承载这些操作的后端。

现有 Docker 工作区和桌面 VM 保留；补入通用的有状态工具服务接口。AutoControl-Arena 和 AgentDojo 的 Python 环境通过该接口暴露原工具，而不是改写成让 target 阅读源码后自己调用函数。服务可以运行在容器内，但容器只是承载方式，目标不因此获得 shell 或源码权限。

共同生命周期为：准备依赖 → 初始化 → 返回初始观察/工具 → 执行动作与接收事件 → 结束并导出 → 评分 → 清理。准备耗时、目标任务耗时、评分耗时分别记录。Gym-Anything 的 post_task/export 必须在 verifier 前按原次序运行。

环境组件提供初始化、工具发现/调用、状态导出、检查和关闭接口；需要恢复能力的协议再要求 checkpoint/restore。状态可以是 Python 数据、数据库、工作区、桌面或其组合，不要求统一重写为一个 JSON 对象。

工具绑定保留名称、参数 schema、返回形式、副作用及权限。截图/图像观察、鼠标键盘动作作为通用消息/动作承载，不把桌面操作自动替换为更强的数据库或 shell 接口。

环境里的 LLM 服务使用明确的模型角色绑定，输入、输出、状态变化进入证据。由服务模拟的一位同事和独立执行的 actor 是不同实现，运行记录必须能区分。

**4. interaction：一个可执行协议容纳静态、多轮、分阶段和自适应任务**

交互协议决定谁在何时收到什么、何时调用目标、何时变更环境、何时结束。提供少量内置驱动：一次响应、固定对话、现有阶段工作流；复杂行为使用带版本的程序或模型策略组件。

不设计需要 Builder 学习的大型流程 DSL。组件接受事件及其获准看到的状态，返回明确动作；框架负责执行动作、检查权限、计费和记录。组件可以由原生 benchmark 包实现，也可以由 Builder 编写，后者不能只能选择预装的 baseline 名称。

共同的控制动作需要覆盖：发送消息、请求目标响应、调用/完成工具、按授权改变环境、注册工具、创建/恢复会话、创建分支、结束任务。谁能使用哪些动作由协议显式授予。普通 actor 不因接口存在就能重写目标系统提示或更改评分规则。

参与者记录身份、策略、初始指令、可见内容、工具权限、历史和状态作用域；目标模型仍是独立的被测角色，其他参与者是任务环境的一部分。被动响应、事件触发和后台活动可由同一调度接口管理。模型与凭据通过运行配置绑定，凭据不属于任务包。

会话状态、环境状态、actor 历史、控制器状态和预算账本分别管理。清空对话不默认重置环境；回滚对话也不意味着撤销数据库副作用。需要恢复哪一部分必须声明，后端不支持时不可假装恢复成功。

Petri 是这套协议的一种组合：审计控制器可以设定目标系统消息、创建模拟工具、发送输入/工具返回、回滚目标会话及结束审计。控制器自己的记忆、已发生的审计事件仍保留。启用 prefill 时分别保存外部预填片段和目标生成片段，不能把拼接后的全部 assistant 文本算作模型输出。目标接口不支持 prefill 就报告能力不匹配；no-prefill 是独立、明确的实验配置。

原定义固定的是策略、权限、资源和评价协议。运行时生成的场景、工具和输入作为实例化事件记录，不回写覆盖原定义。自适应策略在新目标上重新展开；既有轨迹用于审阅，不能冒充新的自适应执行。

预算至少能声明工具调用、模型回合/token、任务时间和控制器的分支/调用限制，并明确计数主体、触发起点、重试与回滚的计费规则。任务自身预算与基础设施超时分别处理。资源耗尽是否评分、如何评分按任务契约执行，网络失败不能自动当成能力失败。

模型访问还需区分生成与给指定续写计算似然。SEA-HELM 所查版本包含后一种模式；它不能用“生成一个选项”替代。不选用这类子任务时无需启用该能力，选择时则由运行配置和模型接口共同验证支持性。

**5. evaluation：参考内容、评分实现和结果各司其职**

参考可以是一个或多个答案、结构化标签、示范轨迹、测试、目标状态或评分准则。标明它是完整允许集合还是示例解。没有唯一文本答案并不是任务不完整；IFBench 可由约束检查器给出完整判分定义。

评分组件接受固定任务定义、模型输出/产物、需要的初末状态和事件证据。实现可以是内置比较器、隔离的原生程序、普通 LLM judge 或可探索环境的 judge agent；允许组合，但必须声明组合方式，不自动平均多个意义不同的分数。

代码型评分适用于任何响应形式。IFBench 使用官方 checkers，LiveBench 使用对应发行版的原评分程序；不必为了运行评分代码把一道纸面生成题包装成 agent 题。

沿用原生组件时保存代码/依赖版本、参数、输入映射、输出解析和原始结果。复杂 evaluator 可以连同依赖作为版本固定的包执行，无须重新实现。组件的入口、参数 schema、输入权限和输出 schema 必须可检查；仅提供一个不透明的“去运行外部仓库”命令不满足契约。

每个指标声明名称、含义、值类型、原生范围、好坏方向、评价对象和适用条件。返回保留原始值、有效性状态、理由及证据引用。实际评估错误与有效的零分分开。

AgentDojo 分别保留 utility 和攻击成功；Who&When 分别保留责任 agent 与步骤结果；Petri 的需求得分与原生 23 维评分分别保存。归一化是显式派生值，不替代原始结果。Analyzer 需要标量时，由运行配置明确选定指标或组合，不能猜测哪个数字代表模型能力。

评分组件的探索与执行使用结束状态的受控副本；评分准备、测试或 judge 探索产生的事件不归到 target 名下。若原生 verifier 会改变状态，保留其运行前证据与变更记录。

集合级指标放在 TaskSuite 的评价计划中。IFBench 的约束级分母、SEA-HELM 的语言/类别聚合，以及可能的 corpus metric，不应硬塞成每题一个分数再取平均。重复运行、Petri 分支和原始独立题目的计数单位分别记录。

**6. EpisodeRecord：配套执行证据，而不是把作答写进任务定义**

任务定义描述实验；执行记录描述这个实验在某次绑定、随机种子和目标模型下发生了什么。已有轨迹导入和新运行输出使用同一证据协议。

执行记录包含：任务内容哈希、实际模型/harness/环境绑定、初始与结束状态引用、最终输出与产物、预算计量、终止原因、评分过程与结果、原生日志引用。

事件采用追加记录：稳定 ID、来源参与者、事件类别、会话/分支、关联调用、父事件和内容引用。保留原始顺序、必要的因果关系及时间信息；日志的接收顺序不伪称所有并发动作的真实先后。回滚改变当前视图，不删除已发生的证据。

至少区分目标生成、预置上下文、外部 prefill、工具真实执行、模型模拟的工具返回、环境干预和评分者操作。工具名相同或消息 role 相同，都不能据此认定来源相同。

Who&When 历史作为 content/asset 使用；本次归因回答另形成 EpisodeRecord。Petri 的互动属于本次 EpisodeRecord，同时记录由控制器实例化的测评内容。这两者不能只因为都有 messages 就混用。

LaaJ 接收由固定定义、原生资产和所选执行记录构成的评估视图，按需读取完整内容。探索操作复用正式环境/评分接口，在独立状态副本中进行。某后端无法启动时允许静态审阅，但明确动态验证未完成，不能用自写的近似环境冒充原环境。

**与现有 EvalClaw 的接入方式**

先提供 v1 → v2 的确定性规范化，保持旧题原来的呈现和运行语义；当前 Docker、VM、actors、干预、workflow、脚本评分和 judge agent 都作为新接口的实现继续使用。转换旧数据时不顺便修改旧评分规则。

Builder 仍通过简短任务模板和已有工具工作。新能力对应新增通用的工具/交互组件创建、注册与验证入口；TaskBuilder 契约根据实际使用的组件要求字段，不让每一道选择题都填写角色、会话和环境。

外部导入器只做字段映射、资源引用和原生组件绑定，不调用 Builder 补写参考解或重做环境。表示校验、运行能力预检、内容质量检查分开：可以导入并审阅一个材料不完整的原始产物，但缺少必要依赖时不能宣称可执行。EvalClaw 自行构题仍可保持更严格的交付要求。

运行前根据任务要求与后端能力进行显式匹配：角色化上下文、工具调用、图像、会话恢复、分支、prefill、似然、环境与评分依赖等。缺能力就报告不支持，不静默更换实验语义。TaskDefinition 的可表达性、某个后端的可执行性，以及一道题是否有效，分别验证。

模型/provider/harness、资源和随机种子放在运行绑定中；任务真正要求的预算或特定能力属于定义。原生 harness 如果包含影响实验的提示、上下文压缩或动作权限，应保存其契约/版本与实际绑定，不能只留下名称。未来换 harness 是显式的新执行条件。

实现按完整路径推进：先统一内容/资源/评分及执行记录，打通全部静态与固定多轮参照；再把现有环境接入共同接口并补齐有状态工具服务，打通 Arena/AgentDojo；最后加入动态控制与分支，打通 Petri。Gym-Anything 沿用原生后端和生命周期，不能以新 Docker 工作区代替它的桌面任务。

这些是一个方案的分步落地，不是只完成 JSON 字段后宣称已经支持所有任务。

**保真与通用性的验收**

每一种已出现的结构变体都建立转换样例，验证以下性质：

1. 相同绑定下，呈现给目标的消息、材料、工具 schema 与权限一致；未授权的参考和实现不可见。
2. 在脚本化的合法与失败动作序列上，原生与转换后的观察、环境变化、结束时机相符。随机或模型驱动部分用可重放的原生响应验证接口，再另作真实运行；不要求两个独立随机 rollout 字面相同。
3. 相同候选回答、状态和轨迹输入给原评分器，原生结果及转换后的原生指标一致。模型 judge 比较输入、配置和结果解析，不能要求两次随机判分必然相等。
4. 会话重设、分支回滚、prefill、工具错误与预算终止都保留来源和边界；不能把恢复后的最后一条分支当成完整执行。
5. 用相同通用接口让 Builder 新建一个任务，而不只验证导入现有 benchmark。该任务能运行、评分并被 LaaJ 检查，才说明能力真正融入 EvalClaw。

预检验证接口、依赖、隔离和已覆盖的行为，不承诺证明任意程序/题目的语义正确性。设计的目标是覆盖可通过数字输入、交互过程和明确评价协议定义的任务；模型缺失的能力、未安装的服务和不可获得的私有材料仍需如实报告。

**核查依据**

- [五个 baseline 的数据与原生材料](https://huggingface.co/datasets/assassinlike/b635)，以及本仓库对应 baseline 源码。
- [MMLU-Pro](https://github.com/TIGER-AI-Lab/MMLU-Pro)：公开数据 schema、作答模板与答案提取。
- [LiveBench](https://github.com/LiveBench/LiveBench/tree/1263ee472f4b9ac3833c0d2f6ad50dd3747fd1df)：Reasoning/Data Analysis 的子任务评分、Coding 的公开/隐藏测试与 Agentic Coding 执行和评估。
- [HLE](https://github.com/centerforaisafety/hle/tree/73ae974b1844c3ffa64c3f4343d9f1f259575700)：公开模型输入与 judge 实现。
- [IFBench](https://github.com/allenai/IFBench/tree/1c40f0c10d9b5c5c2f10a175a28007ebb64f7f4d)：300 条数据结构与 strict/loose 评分。
- [HELM](https://github.com/stanford-crfm/helm/tree/63754d05db6f874e41a395880fb573890a13e791)：Long Context run specs、RULER/∞Bench/MRCR 场景与指标。
- [SEA-HELM](https://github.com/aisingapore/SEA-HELM/tree/9be3986d00185dc6d6ec362b71542ed29642a6be)：语言模板、多轮、生成/分类指标、概率模式与集合聚合。
- [Who&When 数据](https://huggingface.co/datasets/Kevin355/Who_and_When)与[官方实现](https://github.com/mingyin1/Agents_Failure_Attribution/tree/b2bae5c5b06d681d04ea5e9b63b7a30525c04925)：两类原始记录、归因输入构造和 agent/step 评分。
- [AgentDojo](https://github.com/ethz-spylab/agentdojo/tree/089ed468cf3ed0322acc66b0211f26d9d90dbf60)：用户/注入任务、环境初始化、工具、状态/轨迹评分及注入位置约束。
