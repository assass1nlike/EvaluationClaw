# Docker Workspace Environment

Use runtime environment type `docker_workspace`.

- Choose a suitable common image, use `image: "auto"`, or define `image_build` only when a common image is insufficient.
- Put target-visible files that are part of the declared initial environment in `visible_files`, setup-only server/application material in `runtime_files`, and evaluator-only tests in `hidden_files`.
- Every `visible_files` / `runtime_files` / `hidden_files` key is a path relative to `workdir` (e.g. `app/app.py`, `tests/test_regression.py`). Do not use absolute paths or paths outside the workdir; the runtime writes each entry at `workdir/<key>`. So an evaluator script should live at a path like `tests/run_tests.sh`, not `/evaluator/run_tests.sh`.
- Files created or downloaded through construction tools that are task inputs may remain in top-level `assets`; the framework copies them into the container workdir under their filenames. Never put their host paths in the prompt or environment.
- Set `environment.workdir` to an absolute POSIX path inside the container, using `/workspace` unless the task requires another directory; `.` and other relative paths are invalid.
- Use `setup_commands` for bounded initialization and provide the exact `test_command` for deterministic scoring. The preferred evaluator protocol writes `{"score": 0.0-1.0, "passed": true|false, "details": "..."}` to `evaluation.result_path`. A numeric `evaluation.score_path` is also supported. For a JSON object printed as the evaluator's final stdout line, set `evaluation.result_format: "json_on_stdout"`; use `evaluation.score_field` only when its score field is not named `score`.
- During the final evaluator only, `/evalclaw-evidence/episode.json` contains schema `evalclaw.evaluator_evidence.v1`. Its top-level fields are `target`, `target_execution`, `actors`, `interventions`, `timing`, and `termination`. `target_execution` exposes every representation the selected runner has: final response, raw output, stderr, normalized trace and history when available, raw provider responses when available, final state, and tool-call count when known. External harnesses that do not provide a normalized trace leave those fields empty rather than reconstructing one. The runner materializes this path only after the target interaction has ended.
- Use `interventions` when the environment must change independently of the target after the episode starts. Each intervention has a unique `id`, one `trigger`, and one `action`. An elapsed trigger is `{"type":"elapsed_time","after_seconds":30}`. A condition trigger is `{"type":"condition","command":"test -f state/ready","poll_interval_seconds":1}` and fires when its command exits 0. The action is `{"type":"run_command","command":"...","timeout_seconds":20}`. Interventions are one-shot, execute through the runner's Docker control principal rather than `setup_commands`, and are recorded in evaluator evidence. Make actions idempotent enough for direct execution and make condition commands observational.
- For a custom image, use the construction tools to create and verify the Dockerfile and build context. Preserve the returned relative `image_build.context_dir`, `image_build.tag`, and `image_build.enabled=true` in the final environment.
- Set `timeout` (seconds per command) and `max_steps` (maximum interaction steps) appropriate to the workload. The field is named `timeout`, not `timeout_s`.
- If browser interaction is required, configure the canonical browser runtime with a start URL and allowed origins.
- When the TaskDesign requests environment actors, define them under `actors` and define reusable capability groups under `actor_toolsets`. Each actor requires a unique public `id`, a task-specific `system_prompt`, and an optional public `description` and `toolset` reference. The actor does not receive the target's task prompt or transcript; put only the knowledge appropriate to its role in its system prompt. All actor definitions are benchmark content and must not contain provider credentials.
- An actor toolset has `tools`, `read_paths`, `write_paths`, and `network`. Supported actor tools are `list_files`, `read_file`, `write_file`, and `run_command`; paths are workspace-relative roots and network is `none` or `internet`. `run_command` grants access to the complete shared workspace, so its toolset must use `read_paths: ["."]` and `write_paths: ["."]`. Multiple actors may reference the same toolset, and actors with different objective capabilities should reference different toolsets.
- Actor behavior is defined only by its system prompt. Use tool permissions to represent what the role can objectively do, not to guess whether its actions count as helping or completing the target's work. The target can contact any declared actor through one synchronous messaging tool, and each actor retains its own history within the episode.
- Do not build a second scripted-agent, delegation, status, or messaging service alongside environment actors. Actor tasks run through OpenClaw and therefore cannot use `runtime_files`; put shared target-visible state in `visible_files`, role behavior and private role knowledge in each actor's `system_prompt`, and evaluator-only checks in `hidden_files`.
- Ensure the selected image or image build actually contains the declared runtime dependencies, but do not infer capabilities from image names alone.
- Do not expose raw command execution when protected runtime or hidden files exist; use structured workspace tools and runner-private evaluation.
- Keep image-build packages, commands, Dockerfile, and context files only as detailed as required by the TaskDesign.
